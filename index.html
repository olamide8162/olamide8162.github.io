Engineering

Problems worth solving

A waitlist that runs itself

When someone cancels, the next person in line should get the spot without anyone touching the app. I put that rule in the database as a Postgres trigger, so it holds no matter which client makes the change. A second trigger keeps seat counts in sync, and Supabase realtime pushes them to every open Classes screen.

create function promote_from_waitlist()
returns trigger as $$
begin
  if old.status = 'confirmed'
     and new.status = 'cancelled' then
    select id into next_in_line
    from bookings
    where class_id = new.class_id
      and status = 'waitlisted'
    order by created_at limit 1;
    -- first come, first served
    update bookings set status = 'confirmed'
    where id = next_in_line;
  end if;
  return new;
end; $$

Keeping each gym's data private

Turning one gym into many meant every class, booking, exercise and chat message had to belong to a gym. I added a gym_id to each table and scoped every screen to the user's active membership. Row Level Security enforces access in the database, so members only read their own bookings and only staff create classes.

create policy "bookings_read_own"
  on bookings for select
  using (user_id = auth.uid());

// client: scope chat to the member's gym
supabase.from('messages')
  .select('*')
  .eq('gym_id', membership.gym_id)

Finding the nearest gym

The discover map sorts every active gym by real distance using the Haversine formula; gyms without coordinates drop to the bottom instead of breaking the sort. The super admin can bulk-import real gyms for a city, with phone numbers, opening hours and duplicate checks, using Google Places with a SerpAPI fallback.

function haversine(lat1, lon1, lat2, lon2) {
  const R = 6371; // km
  const dLat = (lat2 - lat1) * Math.PI / 180;
  const dLon = (lon2 - lon1) * Math.PI / 180;
  const a = Math.sin(dLat / 2) ** 2
    + Math.cos(lat1 * Math.PI / 180)
    * Math.cos(lat2 * Math.PI / 180)
    * Math.sin(dLon / 2) ** 2;
  return R * 2 * Math.atan2(
    Math.sqrt(a), Math.sqrt(1 - a));
}

Exopleen

A private, installable web app that watches about 700 Solana wallets in real time, logs when they buy a new token, tracks its price for ten days, and pushes an alert at 2x, 5x or 10x. An AI agent scores every new token and learns from its own misses.

React 19 · Vite PWATailwindPython · FastAPISQLiteUbuntu · systemdVercel
The system

Six services, one app

The frontend is a password-gated PWA on Vercel with owner and subscriber roles. Behind it, a cloud Linux server runs six long-lived services: the wallet tracker, a call tracker that checks prices every 3 seconds, a FastAPI backend, a Cloudflare tunnel, a watcher that keeps the tunnel address in sync, and a Telegram ingester for outside signals.

Engineering

Problems worth solving

An AI scorer that learns from its misses

Each new token gets a 0 to 10 score from an LLM agent that pulls market and safety data. Seven days later the system writes a postmortem. After every 20 postmortems, it takes the 100 worst misses (scored 6 or under, went on to 5x or more), asks the model what it overlooked, and adds those rules to every future scoring prompt.

# the feedback loop
buy detected  -> score 0-10
+7 days       -> postmortem(score, outcome)
every 20      -> top 100 false negatives
                 (score <= 6, outcome >= 5x)
              -> synthesise blind-spot rules
              -> inject into next prompts

Filtering out fake pumps

Some tokens showed 5,000x gains that were really wash trades: every milestone fired at the same instant. Real pumps climb gradually, so the tracker now suppresses an alert when more than 7 milestones trigger in one 3-second check, and logs it for review. It caught two fakes straight away.

if len(milestones_this_cycle) > 7:
    # real pumps climb; wash trades teleport
    log("[FakePump]", token)
    continue  # no alert sent
Operations

Running it in production

IncidentCause and fix
App offline for 5+ hoursThe tunnel exited cleanly after a network drop, and the service only restarted on failure. I switched it to always restart and added a watcher that updates the backend address in Vercel Edge Config.
Tracker silently ran with zero walletsA script saved the wallet file as a flat list, but the loader expected an object. I standardised the format and made the database the source of truth.
"Database is locked" across servicesA crashed process left a stale SQLite journal. Restarting the dependent services rolled it back with no data loss.
Database growing past 470 MBA monthly job now removes transactions older than 60 days and runs VACUUM. The first run took it to 261 MB.
Price checks throttledWhen the price API rate-limits the tracker, users get a push warning that alerts may be delayed, at most once an hour.
Deploys interrupted usersNew versions used to reload mid-session. Updates now wait until the app is in the background.
